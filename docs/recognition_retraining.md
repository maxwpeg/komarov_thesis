# README: Механизм дообучения распознавания

## Назначение
Этот документ полностью описывает механизм дообучения распознавания, реализованный в системе для шагов `walls` и `openings`.

Здесь собраны:
- архитектура и жизненный цикл данных;
- роли основных сущностей;
- API и UI-поток;
- структура экспортируемых датасетов и артефактов;
- практические рекомендации по использованию;
- ограничения и типовые проблемы.

Механизм дообучения нужен для того, чтобы система не только сохраняла ручные исправления пользователя, но и превращала их в переиспользуемый обучающий корпус, из которого можно запускать воспроизводимые training-run'ы.

## Что именно реализовано
В системе реализован полный контур:

1. Пользователь исправляет стены или проемы в редакторе плана.
2. Исправленное состояние отправляется как feedback-пример.
3. Пример попадает в общий пул обучающих данных.
4. Оператор на отдельной странице может:
   - просматривать все накопленные примеры;
   - фильтровать их;
   - сравнивать исходное и исправленное состояние;
   - исключать шумные примеры;
   - возвращать их обратно в выборку.
5. Из curated-примеров создается training batch.
6. Для batch запускается отдельный training run в subprocess.
7. На диск сохраняются:
   - экспорт датасета;
   - параметры запуска;
   - лог обучения;
   - итоговые веса;
   - метрики.

При этом production-распознавание автоматически не переключается на обученную модель. Артефакты сохраняются как кандидат для дальнейшей проверки.

## Где это находится в системе
Основные backend-компоненты:

- `backend/services/recognition_training_feedback_service.py`
  Отвечает за сбор feedback, diff, snapshot и экспорт обучающих batch-ов.
- `backend/services/recognition_training_management_service.py`
  Отвечает за обзор, курацию, запуск training-run'ов, сбор датасета и orchestration.
- `backend/routers/recognition_training.py`
  Публичный API для страницы управления дообучением.
- `tools/run_recognition_training.py`
  Standalone runner, который запускается отдельным процессом.

Основные frontend-компоненты:

- `floorplan-ui/src/pages/RecognitionTrainingPage.jsx`
  Страница `/recognition-training`.
- `floorplan-ui/src/api/client.js`
  Клиент для новых recognition-training endpoint'ов.
- `floorplan-ui/src/App.jsx`
  Роут и вход в раздел через navbar.

Хранилище артефактов:

- `outputs/recognition_feedback/<batch_id>`
  Экспортированные batch-ы с manifest и native/derived материалами.
- `outputs/recognition_training/<run_id>`
  Артефакты конкретного запуска обучения.

## Ключевая идея архитектуры
Механизм построен вокруг трех разных сущностей:

### 1. Example
`RecognitionFeedbackExample` — это один обучающий пример, полученный из ручной правки пользователя.

Он хранит:
- исходный snapshot детектора;
- исправленный snapshot;
- diff между ними;
- теги проблемы;
- заметки;
- оценку сложности `hardness_score`;
- статус курации.

Важно: example — это именно единица данных для обучения, а не запуск обучения.

### 2. Batch
`RecognitionTrainingBatch` — это конкретный экспортированный срез датасета для одного шага (`walls` или `openings`).

Batch нужен, чтобы зафиксировать:
- какие именно examples были выбраны;
- какой набор файлов был собран;
- где лежит manifest;
- какой это был экспорт по времени и составу.

Один и тот же example может попасть в несколько batch-ов. Для этого используется связующая таблица `RecognitionTrainingBatchExample`.

### 3. Run
`RecognitionTrainingRun` — это один запуск обучения по одному batch.

Run хранит:
- `run_id`;
- шаг (`walls` или `openings`);
- статус;
- конфиг обучения;
- путь к логам;
- путь к артефактам;
- summary метрик;
- ошибку, если run завершился неуспешно.

Разделение `example -> batch -> run` нужно для воспроизводимости:
- example — исходные данные;
- batch — зафиксированный набор данных;
- run — конкретная попытка обучения на конкретном наборе.

## Почему механизм устроен именно так
### Почему есть отдельная страница
Дообучение работает на общем корпусе примеров по всей системе, а не по одному проекту. Поэтому управление им вынесено на глобальную страницу `/recognition-training`.

### Почему используется `Exclude`, а не удаление
Удаление разрушало бы историю. Пример мог уже участвовать в batch или run. Поэтому оператор может исключить его из будущих запусков, но при этом не ломать воспроизводимость старых обучений.

### Почему обучение запускается в subprocess
Обучение не выполняется внутри FastAPI-запроса, потому что:
- HTTP-запрос не должен висеть до конца тренировки;
- API-процесс не должен блокироваться тяжелой задачей;
- лог run-а должен существовать отдельно от жизненного цикла запроса;
- аварии training-run-а не должны убивать веб-сервер.

### Почему нет автоматической активации модели
Система пока сохраняет обученную модель как артефакт. Production-переход на новый инференс — отдельная задача. Это сделано сознательно, чтобы не подменять рабочий распознаватель без отдельной валидации.

## Полный жизненный цикл данных
### Шаг 1. Детекция и валидация
Пользователь проходит обычный pipeline в редакторе.

Для шага `walls` или `openings` система хранит:
- текущее состояние pipeline;
- revision шага;
- snapshot детектора (`PipelineDetectionSnapshot`).

Feedback можно отправить только после того, как шаг валидирован.

### Шаг 2. Отправка feedback
Когда пользователь нажимает кнопку отправки для дообучения:
- система берет исходный snapshot детектора;
- берет текущее исправленное состояние объектов на плане;
- вычисляет `diff_summary`;
- сохраняет `RecognitionFeedbackExample`.

Если snapshot для старого плана отсутствует, система умеет сделать legacy-backfill, чтобы feedback не падал на старых данных.

### Шаг 3. Курация
После этого пример появляется на странице `/recognition-training`.

Оператор может:
- посмотреть список;
- открыть detail;
- прочитать теги и заметки;
- оценить diff;
- исключить пример (`excluded`);
- вернуть обратно (`approved`).

В batch попадают только примеры со статусом курации `approved`.

### Шаг 4. Формирование batch
При запуске обучения система:
- выбирает step;
- проверяет, нет ли уже активного run;
- отбирает eligible curated-примеры;
- экспортирует их в `outputs/recognition_feedback/<batch_id>`;
- создает `RecognitionTrainingBatch`;
- создает связи `RecognitionTrainingBatchExample`.

### Шаг 5. Создание run
После экспорта batch создается `RecognitionTrainingRun` со статусом `queued`, и отдельным процессом запускается:

```bash
python tools/run_recognition_training.py --run-id <run_id>
```

### Шаг 6. Сбор обучающего датасета
Runner читает batch и собирает YOLO-датасет в:

```text
outputs/recognition_training/<run_id>/dataset
```

### Шаг 7. Запуск обучения
Runner запускает Ultralytics и сохраняет результаты в директорию run-а.

### Шаг 8. Сохранение результатов
После завершения run обновляются:
- статус run;
- summary метрик;
- статус batch;
- `used_at` у примеров, которые действительно участвовали в run.

## Какие сущности хранятся в БД
### `PipelineDetectionSnapshot`
Назначение:
- immutable-снимок результата детектора для конкретного `step_revision`.

Нужен для того, чтобы feedback сравнивал исправленное состояние не с текущим DB-состоянием, а с тем, что реально выдал детектор.

### `RecognitionFeedbackExample`
Назначение:
- единица обучающих данных.

Хранит:
- `step`;
- `step_revision`;
- `source_snapshot`;
- `corrected_snapshot`;
- `diff_summary`;
- `issue_tags`;
- `notes`;
- `hardness_score`;
- `status`;
- `curation_status`;
- временные метки отправки, экспорта и использования.

### `RecognitionTrainingBatch`
Назначение:
- фиксированное описание экспортированного набора данных.

Хранит:
- `batch_id`;
- `step`;
- `status`;
- `export_dir`;
- `summary`.

### `RecognitionTrainingBatchExample`
Назначение:
- связь many-to-many между batch и example.

Это позволяет:
- переиспользовать один example в нескольких batch;
- не терять историю старых экспортов;
- не зависеть от legacy-поля `training_batch_id`.

### `RecognitionTrainingRun`
Назначение:
- один запуск обучения.

Хранит:
- `run_id`;
- `training_batch_id`;
- `step`;
- `status`;
- `config`;
- `metrics_summary`;
- `artifact_dir`;
- `log_path`;
- `error_message`;
- времена постановки, старта и завершения.

## Статусы и их смысл
### Статусы example
Используются два независимых измерения:

1. `status`
   Это технический жизненный цикл примера:
   - `approved`
   - `exported`
   - `used`

2. `curation_status`
   Это операторское решение:
   - `approved`
   - `excluded`

Ключевой момент:
- `curation_status=approved` означает, что пример можно использовать в новых batch;
- `curation_status=excluded` означает, что пример остается в истории, но не идет в новые запуски.

### Статусы run
- `queued`
- `running`
- `succeeded`
- `failed`
- `canceled`

В текущей реализации система не позволяет запускать второй run, пока первый еще `queued` или `running`.

## Как выбираются примеры для batch
Система не берет все подряд. Она использует эвристику отбора.

### Общий принцип
Для каждого шага сначала отбираются только examples, у которых:
- `curation_status == approved`

Затем выборка строится так:
- все примеры с реальным изменением `diff_summary.changed == true`;
- плюс ограниченное количество unchanged-примеров;
- unchanged добавляются максимум в соотношении 4:1 к changed.

Это позволяет:
- не терять сложные исправления;
- не раздувать датасет пустыми или почти пустыми примерами.

### Пороговые условия для `walls`
- минимальный порог по количеству approved selected examples: `50`
- альтернативный порог по hard-примерам при длительном простое: `10`
- минимальная доля реальных исправлений: `0.2`
- idle window: `14` дней

### Пороговые условия для `openings`
- минимальный порог по approved selected examples: `75`
- альтернативный режим по простоям:
  - минимум `200` размеченных проемов;
  - должны быть и `door`, и `window`;
  - idle window: `14` дней
- минимальная доля реальных исправлений: `0.2`

### Зачем показывается readiness hint
На summary-карточках система показывает причину, почему batch:
- уже готов;
- еще не готов;
- упирается в число примеров;
- упирается в долю реальных исправлений;
- ожидает больше данных.

Это помогает оператору не гадать, когда запуск уже имеет смысл.

## Как выглядит экспорт batch
Каждый batch экспортируется в:

```text
outputs/recognition_feedback/<batch_id>
```

Там лежат:
- `images/`
- `native/source/`
- `native/corrected/`
- `derived/`
- `manifest.jsonl`

### Что лежит в `manifest.jsonl`
Для каждого sample в manifest есть:
- `sample_id`
- `floor_plan_id`
- `step`
- `step_revision`
- `detector_version`
- `split`
- `image_path`
- `source_snapshot_path`
- `corrected_snapshot_path`
- `diff_summary`
- `issue_tags`
- `hardness_score`
- `curation_status`
- `derived`

### Что экспортируется для `walls`
Для `walls` сохраняются:
- исходное изображение плана;
- native JSON snapshots;
- mask-файлы стен;
- centerlines JSON.

При этом основной train-input в run-е строится как full-plan segmentation polygons.

### Что экспортируется для `openings`
Для `openings` сохраняются:
- исходное изображение плана;
- native JSON snapshots;
- ROI-crops и annotation JSON.

Эти ROI-файлы нужны как debug/QA-материал, но основной train-input для run-а строится как full-plan labels для `door` и `window`.

## Как строится датасет для обучения
Runner собирает YOLO dataset в:

```text
outputs/recognition_training/<run_id>/dataset
```

Структура:

```text
dataset/
  images/
    train/
    val/
    test/
  labels/
    train/
    val/
    test/
  dataset.yaml
```

### Для `walls`
Используется full-plan segmentation:
- один класс: `wall`
- аннотации строятся как polygons из исправленных стен

### Для `openings`
Используется full-plan segmentation/instance labels:
- класс `0`: `door`
- класс `1`: `window`
- аннотации строятся из исправленных bbox проемов

### Разбиение на train/val/test
Split вычисляется детерминированно по `floor_plan_id`, чтобы:
- один и тот же план стабильно попадал в один и тот же split;
- разбиение не “прыгало” между повторными запусками.

## Конфигурация обучения
Оператор может менять только:
- `epochs`
- `imgsz`
- `batch`
- `patience`

Остальное зафиксировано на сервере.

### Дефолты для `walls`
- `model = yolov8n-seg.pt`
- `epochs = 80`
- `imgsz = 1024`
- `batch = -1`
- `patience = 15`
- `device = auto`
- `auto` автоматически резолвится в `0`, если `torch.cuda.is_available() == True`, иначе в `cpu`
- если CUDA видна, но `torchvision.ops.nms` на GPU недоступен или несовместим, `auto` принудительно переключается на `cpu`, чтобы training-run не падал на старте
- если весь batch собран из одного floor plan или manifest даёт пустой `train`/`val`, training dataset автоматически перераскладывается в рабочие split’ы; для одного уникального примера он дублируется в `val`
- при сборке training dataset исходные изображения дополнительно нормализуются в `.png`, поэтому файлы вроде `.jfif` не ломают Ultralytics loader

### Дефолты для `openings`
- `model = yolov8n-seg.pt`
- `epochs = 120`
- `imgsz = 1280`
- `batch = -1`
- `patience = 20`
- `device = auto`
- `auto` автоматически резолвится в `0`, если `torch.cuda.is_available() == True`, иначе в `cpu`
- если CUDA видна, но `torchvision.ops.nms` на GPU недоступен или несовместим, `auto` принудительно переключается на `cpu`, чтобы training-run не падал на старте
- если весь batch собран из одного floor plan или manifest даёт пустой `train`/`val`, training dataset автоматически перераскладывается в рабочие split’ы; для одного уникального примера он дублируется в `val`
- при сборке training dataset исходные изображения дополнительно нормализуются в `.png`, поэтому файлы вроде `.jfif` не ломают Ultralytics loader

## Какие файлы сохраняются после run
В директории:

```text
outputs/recognition_training/<run_id>
```

сохраняются:
- `params.json`
  Полное описание запуска, batch и конфигурации.
- `metrics.json`
  Результаты run-а.
- `stdout.log`
  Консольный лог обучения.
- `best.pt`
  Лучшие веса.
- `last.pt`
  Последние веса.
- `dataset/`
  Собранный обучающий датасет, использованный в run-е.

## Публичный API
### Feedback из pipeline
Эти endpoint'ы продолжают собирать обучающие примеры:

- `POST /api/floor-plans/{floor_plan_id}/pipeline/walls/feedback`
- `POST /api/floor-plans/{floor_plan_id}/pipeline/openings/feedback`
- `POST /api/floor-plans/{floor_plan_id}/pipeline/{step}/feedback`

### Overview и список данных
- `GET /api/recognition-training/overview`
  Возвращает summary по `walls` и `openings`.

- `GET /api/recognition-training/examples`
  Возвращает легкий список примеров.

- `GET /api/recognition-training/examples/{id}`
  Возвращает detail конкретного примера.

### Курация
- `PATCH /api/recognition-training/examples/{id}`
  Обновляет:
  - `curation_status`
  - `issue_tags`
  - `notes`

- `POST /api/recognition-training/examples/bulk-curate`
  Массово меняет `curation_status` у набора примеров.

### Запуски обучения
- `GET /api/recognition-training/runs`
  Список run-ов.

- `GET /api/recognition-training/runs/{run_id}`
  Detail run-а.

- `GET /api/recognition-training/runs/{run_id}/log?tail=200`
  Хвост лога.

- `POST /api/recognition-training/runs`
  Ставит новый run в очередь и запускает subprocess.

## Как пользоваться через UI
### 1. Сначала накопите полезные примеры
В редакторе плана:
- доведите шаг `walls` или `openings` до валидированного состояния;
- исправьте ошибки распознавания;
- нажмите кнопку отправки для дообучения.

Так вы наполните общий корпус examples.

### 2. Откройте страницу `/recognition-training`
На странице есть четыре основные зоны.

#### Summary cards
По одному блоку для `walls` и `openings`.

Показывают:
- число approved examples;
- число excluded examples;
- сколько examples сейчас selected for batch;
- readiness hint;
- последний успешный run;
- дефолты обучения.

#### Таблица примеров
Позволяет:
- фильтровать по шагу;
- фильтровать по статусу курации;
- фильтровать по проекту и плану;
- включать только реальные исправления;
- искать по проекту, коду, тегам и заметкам;
- сортировать по дате или hardness.

#### Карточка примера
Показывает:
- исходное изображение плана;
- overlay исходного и исправленного состояния;
- теги;
- заметки;
- историю batch;
- историю run.

Режимы overlay:
- `source`
- `corrected`
- `diff`

#### Панель run-ов
Показывает:
- список запусков;
- их статус;
- sample count;
- лог выбранного run-а.

### 3. Выполните курацию
Практически правильный порядок такой:

1. Включите фильтр `Только реальные исправления`.
2. Отсортируйте по `hardness`.
3. Откройте самые “тяжелые” и подозрительные примеры.
4. Исключите:
   - дубли;
   - неаккуратные ручные правки;
   - тестовый мусор;
   - шумные случаи, где корректировка не несет полезного сигнала.
5. Сохраняйте заметки и теги так, чтобы по ним можно было искать проблемные классы ошибок.

### 4. Запустите обучение
На карточке нужного шага:
- проверьте readiness hint;
- убедитесь, что нет активного run;
- при необходимости подправьте `epochs`, `imgsz`, `batch`, `patience`;
- нажмите кнопку запуска.

После этого:
- создастся batch;
- создастся run;
- стартует subprocess;
- лог начнет появляться на странице.

### 5. Проверьте результат
После завершения откройте run и посмотрите:
- статус;
- лог;
- метрики;
- `best.pt`;
- `metrics.json`.

Правильная интерпретация результата:
- это артефакт-кандидат;
- он еще не является автоматически новой production-моделью.

## Рекомендуемый рабочий процесс
### Режим “накопление корпуса”
Подходит, когда идет поток правок по многим планам.

Рекомендации:
- регулярно отправляйте feedback из редактора;
- не запускайте обучение слишком рано;
- сначала накопите корпус реальных исправлений.

### Режим “очистка перед запуском”
Подходит перед run-ом.

Рекомендации:
- фильтр `changed only`;
- сортировка по `hardness`;
- bulk `Exclude` для мусора;
- ручной просмотр пограничных примеров.

### Режим “повторный run”
Подходит, если:
- накопились новые examples;
- прошлый run был давно;
- нужно проверить другой набор гиперпараметров.

Поскольку examples переиспользуемые, система хранит историю независимо по batch и run.

## Практические советы
### Когда имеет смысл запускать `walls`
Когда:
- накопились реальные исправления по геометрии стен;
- есть тяжелые случаи;
- readiness hint перестал говорить, что данных мало.

### Когда имеет смысл запускать `openings`
Когда:
- в датасете есть и `door`, и `window`;
- накопилось достаточно разметки;
- много реальных восстановлений/исправлений проемов.

### Как использовать заметки и теги
Хорошая практика:
- `missed`
- `false_positive`
- `wrong_class`
- `wrong_wall_link`
- `geometry_shifted`

Так по корпусу можно быстро находить повторяющиеся типы ошибок.

### Что лучше исключать
Лучше исключать:
- случайные черновые правки;
- учебные планы;
- дубли одного и того же кейса без дополнительной ценности;
- примеры, где исправление не отражает реальную целевую разметку.

## Ограничения текущей версии
- Поддерживаются только шаги `walls` и `openings`.
- Одновременно разрешен только один активный training run на всю систему.
- Аутентификации и ролевой модели нет.
- Автор курации и запуска не сохраняется.
- Автоматическая активация новой модели отсутствует.
- Обучение предполагает локальную машину, на которой запущен backend.

## Что важно помнить оператору
- Если пример исключен, он не удален: он просто не попадет в будущие batch-ы.
- Если run завершился успешно, это еще не означает автоматический production rollout.
- Если предыдущий run активен, новый run запустить нельзя.
- Если batch “не готов”, это обычно означает, что корпус данных еще недостаточно качественный или недостаточно большой.

## Типовые проблемы и что делать
### На странице нет новых роутов или 404
Причина:
- backend не перезапущен после обновления.

Что делать:
- перезапустить FastAPI/uvicorn процесс.

### Run не стартует
Проверьте:
- нет ли уже `queued` или `running` run;
- существует ли базовая модель `yolov8n-seg.pt`;
- доступны ли файлы исходных изображений;
- готов ли batch по readiness conditions.

### Run упал со статусом `failed`
Смотрите:
- `stdout.log`
- `error_message` в run
- `metrics.json`, если он успел появиться частично

### Не удается собрать batch
Типовые причины:
- слишком мало approved examples;
- слишком мало реальных исправлений;
- для `openings` недостаточно размеченных `door/window`;
- часть примеров исключена из выборки.

### Картинка примера не отображается
Проверьте:
- существует ли файл в `uploads/...`;
- смонтирован ли `/uploads` в backend;
- не удален ли исходный план.

## Краткий сценарий использования
Если нужен самый короткий правильный путь:

1. Исправляйте стены и проемы в редакторе.
2. Отправляйте их как feedback.
3. Откройте `/recognition-training`.
4. Отфильтруйте `changed only`.
5. Исключите шумные примеры.
6. Убедитесь, что readiness hint положительный.
7. Запустите training run.
8. Следите за логом.
9. После завершения изучите `metrics.json` и `best.pt`.

## Итог
Реализованный механизм дообучения — это не просто экспорт исправлений, а полный управляемый контур:
- сбор сигналов из пользовательских правок;
- хранение примеров как переиспользуемого корпуса;
- ручная курация;
- воспроизводимые batch-экспорты;
- отдельные training-run'ы;
- сохранение артефактов и истории.

Это позволяет постепенно превращать ручные исправления в систематический источник улучшения распознавания, не ломая основной pipeline и не подменяя production-логику без дополнительной проверки.
## Обновление: рекомендованный batch и принудительный запуск

- На странице `/recognition-training` для каждого шага теперь показывается `Recommended batch`.
- Если оператор запускает обучение до достижения рекомендуемого размера batch или при отрицательном readiness-hint, UI показывает подтверждение и отправляет запуск с флагом `force=true`.
- Backend при `force=true` разрешает собрать batch и создать run даже ниже обычного порога готовности, если в выборке есть хотя бы один approved-пример.
- Флаг принудительного запуска сохраняется в конфиге run и в summary batch, чтобы такой запуск было видно в истории и артефактах.
