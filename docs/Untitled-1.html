Фронтенд

  • Пользователь (Инженер, Разработчик).
    Это внешний актор системы. Инженер работает с проектами и планами, разработчик дополнительно видит дообучение, очередь задач и пользователей. Плюс такого разделения в том, что сложные и опасные функции не доступны всем подряд. Минус: нужно поддерживать роли и проверки доступа. Связь: пользователь работает только через React SPA.

  • React SPA.
    Это единое клиентское приложение на React, которое работает без полной перезагрузки страницы. Технологии: React, react-router-dom, fetch, контекстное состояние. Плюсы: быстрый UX, единый стиль, переиспользуемые компоненты. Минусы: часть логики состояния переносится на клиент, нужно аккуратно управлять синхронизацией с сервером. Связь: это главный контейнер, внутри которого живут маршрутизация, авторизация, редактор, обучение, preview PDF и API-клиент.

  • AuthContext / сессия.
    Отвечает за восстановление и хранение текущей пользовательской сессии. При старте вызывает /api/auth/me, при 401 сбрасывает состояние. Технологии: React Context, cookie-based session, глобальный unauthorized handler. Плюсы: авторизация централизована, не размазана по страницам. Минусы: фронтенд зависит от корректной работы cookie-сессии и обработчика 401. Связь: влияет на показ страниц, ролей и навигации.

  • Маршрутизация и страницы.
    Это слой, который решает, какой экран показывать: проекты, карточка проекта, редактор этажа, каталог оборудования, дообучение, очередь задач, пользователи. Технологии: React Router. Плюсы: чистое разделение экранов и URL. Минусы: при росте проекта растет число состояний и переходов. Связь: маршруты вызывают API-клиент и используют контексты.

  • REST API клиент.
    Это тонкий слой над fetch, который делает GET/POST/PATCH/DELETE, отправляет cookie и统一но обрабатывает ошибки. Плюсы: нет дублирования HTTP-логики по всему интерфейсу. Минусы: это не полноценный data layer уровня React Query, поэтому кеширование и ретраи реализованы вручную. Связь: все страницы ходят в бэкенд именно через него.

  • Окна и уведомления.
    Это внутренний слой DialogProvider: toast, confirm, prompt. Он заменяет браузерные alert/confirm/prompt на UI в стиле приложения. Плюсы: единый визуальный стиль, контроль UX, предсказуемость. Минусы: нужно отдельно обслуживать доступность и поведение модалок. Связь: используется страницами проектов, обучения, редактора и каталога.

  • Опрос фоновых задач.
    Это клиентский polling: фронтенд раз в небольшой интервал спрашивает статус задачи у /api/background-tasks/{id} и обновляет экран. Технология: периодический GET, без WebSocket. Плюсы: простота, надежность, легко отлаживать, для 3-5 пользователей этого достаточно. Минусы: есть лишние запросы и небольшая задержка обновления. Связь: используется для PDF, распознавания, pipeline-этапов, дообучения.

  • Редактор плана.
    Это специализированный экран для работы с этажом: стены, проемы, помещения, ЗКСПС, извещатели, СОУЭ, маршруты. По сути это главный рабочий инструмент инженера. Методы: визуальное редактирование, ручная коррекция, подтверждение этапов pipeline. Плюсы: human-in-the-loop, то есть пользователь не зависит от “черного ящика” и может исправить результат. Минусы: редактор - самый сложный UI по состояниям и геометрии. Связь: получает данные этажа, вызывает detection/commit-операции и читает pipeline state.

  • Дообучение.
    Это developer-only экран для управления примерами обратной связи, пакетами обучения, запусками и активацией моделей. Технологии: REST + polling. Алгоритмы: подготовка датасета, разбиение train/val/test, запуск обучения Ultralytics YOLO, чтение логов и метрик. Плюсы: система становится самоулучшаемой. Минусы: требует инфраструктуры данных и аккуратной валидации качества. Связь: использует recognition feedback, background tasks, storage и active models.

  • Проекты и PDF preview.
    Это слой проектных карточек и просмотра PDF. Важно: preview открывает не “другой документ”, а нужную страницу уже сгенерированного проектного PDF. Плюсы: единый итоговый источник истины для печати и просмотра. Минусы: генерация тяжелая, поэтому выполняется через очередь. Связь: работает с проектами, PDF API, asset endpoints и background tasks.

Бэкенд

  • FastAPI.
    Это главный HTTP-вход в систему. Он маршрутизирует запросы, проверяет доступ, вызывает use cases и отдает JSON или файлы. Технологии: FastAPI, SQLAlchemy, dependency injection. Плюсы: быстрый запуск, ясная структура REST API, удобная валидация схемами. Минусы: при росте проекта нужно строго держать архитектурные границы, иначе все превратится в “толстый app.py”. Связь: это точка входа для фронтенда.

  • Роутеры API.
    Они разделяют домены по смыслу:
    auth/users - вход, текущий пользователь, управление учетными записями;
    projects - карточки проектов;
    floor-plans - этажи и их загрузка;
    elements - геометрические объекты на плане;
    equipment - каталог оборудования и файлы;
    pipeline - пошаговое распознавание и подтверждение этапов;
    recognition - полное распознавание и сбор feedback;
    training - примеры, batch, run, active model;
    pdf - проектные документы и preview;
    assets - защищенная выдача файлов;
    background-tasks - статусы очереди.
    Плюс такого разбиения - хороший модульный контур. Минус - нужно следить, чтобы логика не дублировалась между роутером и сервисом.

  • Project Service.
    Управляет CRUD проекта, владельцем, проектными документами и связанными сущностями. Это доменный сервис, а не просто SQL-обертка. Плюс: проект становится центром предметной модели. Минус: на нем завязано много функциональности. Связь: с проектами, этажами, оборудованием, PDF.

  • Floor Plan Service.
    Управляет загрузкой и параметрами этажей: изображение, размеры, масштаб, высота, связь с проектом. Плюс: отдельная зона ответственности для этажей. Минус: масштаб и геометрия чувствительны к качеству исходного изображения. Связь: с storage, project service, pipeline и editor.

  • Pipeline Service.
    Это оркестратор пошаговой обработки плана: стены -> проемы -> помещения -> ЗКСПС. Он отделяет “обнаружить” от “подтвердить”. Методы и алгоритмы: препроцессинг изображения, морфология, OCR размеров, детекция стен, поиск разрывов вдоль стен, классификация проемов, contour-based detection помещений, state machine этапов. Плюсы: объяснимость, поэтапная валидация, возможность ручной коррекции. Минусы: сложнее, чем один black-box inference; нужен UX для каждого шага. Связь: с floor plan, editor, feedback и recognition/training.

  • Recognition Service.
    Это сценарий полного автоматического распознавания плана за один запуск. Он использует интегратор распознавания, преобразует результат в сущности БД и сохраняет артефакты. Технологии и алгоритмы: OpenCV, OCR, геометрические преобразования, интеграция с floorplan module; при наличии активной модели часть шагов может идти через дообученный детектор. Плюсы: быстрый старт и автоматизация. Минусы: чувствителен к шуму, качеству скана и разнообразию планов. Связь: с queue/worker, floor plans, storage, feedback examples.

  • Training Service.
    Это сервис управления жизненным циклом дообучения. Алгоритмы: отбор примеров, экспорт batch, генерация датасета в формате YOLO, автоматическое разбиение train/val/test, запуск Ultralytics YOLO, сбор метрик, активация лучшего чекпоинта. Технологии: Ultralytics, PyTorch, файловые артефакты, метрики, логи. Плюсы: модель улучшается на реальных исправлениях пользователей. Минусы: нужно контролировать качество размеченных данных и reproducibility. Связь: с feedback, background tasks, storage, active models.

  • PDF Service.
    Генерирует итоговый комплект проектных документов и умеет вычислять, на какой странице находится конкретный этап для preview. Важный принцип: preview не создает новый PDF на каждый клик, а использует последний сгенерированный документ и только ищет нужную страницу. Плюсы: единый итоговый артефакт, меньше рассинхронизации. Минусы: если PDF устарел, его надо сначала пересобрать. Связь: с projects, documents, storage, assets, worker.

  • Storage Service.
    Это абстракция хранения файлов: изображения этажей, изображения оборудования, PDF, логи, артефакты обучения. Сейчас логика уже отделена от UI и выдает asset_url, а не локальный путь. Это очень правильно архитектурно. Плюсы: фронтенд не знает о файловой системе сервера, легче миграция на объектное хранилище. Минусы: нужно поддерживать жизненный цикл файлов и чистку артефактов. Связь: практически со всеми доменами.

  • Очередь задач / Worker.
    Это ключевой оптимизационный элемент. HTTP-запрос не ждет тяжелую операцию, а ставит задачу в таблицу background_tasks; worker забирает ее, выполняет и пишет результат. Методы: FIFO по времени создания, статусы queued/running/succeeded/failed/canceled, dedupe_key для недопущения дубликатов. Плюсы: UI не зависает, сервер устойчивее под нагрузкой, операции наблюдаемы. Минусы: нужен polling, мониторинг и аккуратная обработка ошибок. Связь: между API, доменными сервисами, БД и storage.

  • Распознавание / Дообучение модели / Генерация PDF.
    Это типовые тяжелые фоновые задачи. Они вынесены отдельно, потому что затратны по CPU/GPU/IO. Плюсы: одинаковая модель управления для разных типов нагрузки. Минусы: сложнее трассировка, чем у синхронного вызова. Связь: запускаются через API, исполняются worker'ом, результаты сохраняют в БД и storage.

  • PostgreSQL / БД.
    На схеме это обозначение основной реляционной БД приложения. По смыслу она хранит проекты, этажи, элементы, состояния pipeline, run'ы обучения, активные модели, очередь задач и связи между ними. Плюсы: транзакционность, согласованность данных, связи, фильтрация и аудит. Минусы: схема сложнее, чем у file-based хранения. Важная честная оговорка: в коде есть SQLAlchemy и fallback на SQLite, но для production-логики такого типа правильная целевая БД - PostgreSQL.

  • S3-совместимое хранилище.
    На схеме это объектное хранилище для файлов и артефактов. Архитектурно смысл правильный: файлы отделяются от вычисляющей машины. В текущем коде уже есть объектная модель путей и asset proxy, но фактическая реализация пока ближе к локальному object-storage каталогу, чем к настоящему S3/MinIO. Плюсы: масштабируемость, независимость от локального диска контейнера/сервера. Минусы: требует отдельного жизненного цикла, прав доступа и очистки объектов. Связь: с PDF, training, equipment, floor plans, asset endpoints.

  • Assets / PDF endpoints.
    Это защищенные URL вида /api/assets/..., через которые фронтенд получает файлы по backend-issued URL, а не по прямому пути на диск. Плюсы: безопасность, единый контракт, возможность скрыть реальное хранилище. Минусы: backend становится прокси для файловой раздачи. Связь: с storage и frontend preview.

Какие алгоритмы здесь реально дают “интеллект”

  • Для обработки плана используются классические CV-методы: preprocess, Canny, HoughLinesP, морфологические операции, contour detection, OCR размеров через Tesseract, геометрическая привязка размеров к стенам.
  • Для дообучения используются модели Ultralytics YOLO; сервис сам собирает датасет, пишет dataset.yaml, готовит train/val/test, запускает обучение и сохраняет best.pt, last.pt, metrics.json.
  • Для ЗКСПС используется геометрическое объединение полигонов помещений через Shapely unary_union, поэтому внутренние границы скрываются, а отображается внешний контур зоны.
  • Для автопроектирования сигнализации и СОУЭ применяются эвристики и геометрические политики, а не просто ручная расстановка.

Почему эта архитектура вообще ценна

  • Она объяснимая: можно показать, где именно принимается каждое решение.
  • Она расширяемая: это модульный монолит, а не хаотичный монолит.
  • Она устойчива к нагрузке: тяжелые действия вынесены в очередь.
  • Она поддерживает цикл улучшения качества: пользователь исправил результат -> это стало training data -> модель можно улучшить.
  • Она отделяет данные от вычислений: БД хранит структуру, storage хранит бинарные артефакты.

Что честно сказать про ограничения на защите

  • Polling проще WebSocket и для 3-5 пользователей оправдан, но для большого числа активных пользователей WebSocket был бы эффективнее.
  • Очередь уже есть, но для truly production multi-worker режима лучше усиливать claim-механику блокировками уровня PostgreSQL.
  • Абстракция object storage уже правильная, но фактическую реализацию стоит довести до полноценного MinIO/S3.
  • OCR и CV чувствительны к качеству входных планов; это не магия, а инженерный компромисс.
  • Модульный монолит выбран осознанно: для этого масштаба он выгоднее микросервисов по сложности эксплуатации.
